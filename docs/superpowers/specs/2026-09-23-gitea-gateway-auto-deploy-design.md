# Gitea main 自动部署网关 Web

## 目标与边界

GitHub `sc1994/Trading-Agents-Web` 仍是代码权威源。GitHub `main` 更新后，现有同步工作流将同一完整 SHA 推送至 Gitea `suncheng/Trading-Agents-Web` 的 `main`。该 Gitea push 自动在 `gateway` Runner 上构建、验证并部署 Web。PR 更新不部署；不通过 GitHub 构建产物传递镜像。

服务保留 `127.0.0.1:7681:8080`，本次不改代理、域名、端口或应用身份认证。用户明确负责公网可达性及入口配置；回环绑定不等于私网隔离，既有代理仍可能转发该端口。工作台含服务器端凭据，若公开访问则有暴露风险，不把自动部署描述为入口安全验证。

## 发布流程

1. Gitea 工作流只响应目标仓库 `main` 的 `push`，固定 `gateway` Runner、只读 checkout 权限、现有同组串行设置；检出事件的完整 SHA，核验与 `git rev-parse HEAD` 一致。不得接受不明仓库、其他分支或手工传入的任意 SHA。
2. 移除只适用于 `workflow_dispatch` 的两项 SHA 人工声明和部署脚本的对应环境变量前置门禁。部署脚本仍要求恰好一个完整的小写 SHA，并在 Docker 操作前校验；镜像 revision 标签与之相同。
3. 保留既有端口冲突检查、非 root 候选容器、临时数据卷、健康及页面逐字节检查、Compose 发布健康检查和失败后的旧镜像回退。不得清理生产卷或运行全局 prune。首次部署失败时报告失败并停止失败服务；升级失败时按现有脚本恢复旧镜像，不声称回退数据。
4. 合并后新代码同步至 Gitea 的 push 才触发部署；合并前的 GitHub PR 验证不触发。GitHub 合并后的 CI 可能与 Gitea 部署并行，不能声称部署等待其通过。若首次 Gitea Runner 不兼容声明的工作流语法或部署环境，工作流必须失败而不是静默跳过。

## 验证与文档

更新基础设施测试，覆盖 Gitea `push`/`main`/仓库限制、检出 SHA、无人工门禁、固定回环端口及现有候选/回退路径；先观察旧行为的失败，再实施改动。运行专项测试、全量测试及 lint，提交到新 PR 并检查 GitHub CI。发布后只读核对 Gitea 工作流结论、网关 Compose 容器的镜像 revision/健康状态及 `127.0.0.1:7681/healthz`；不得仅凭同步成功认定已部署。若现场配置与文档不一致，停止变更并报告漂移。

更新运维手册顶部的当前发布边界，明确旧人工流程为历史资料，不再要求人工填写 SHA；仍提示公开入口与无登录保护的风险。此次设计不授权直接操作生产代理、Runner、持久卷或手工触发部署。
